# Spec Delta

## Purpose

Gives a thread's owner a short summary of what the agent did while they were away, for threads of any agent provider, so they can pick the thread up without rereading the transcript.

## ADDED Requirements

### Requirement: Recap is offered after an absence with new activity

The thread view SHALL offer a recap when the viewing user owns the thread, the thread has assistant messages or tool calls newer than the user's last read time of that thread, and that last read time is at least 5 minutes old. A thread the user has never read SHALL count as read at its creation time. No recap SHALL be offered for a thread with no new activity.

#### Scenario: Owner returns after the agent worked

- **WHEN** the owner opens a thread they last read 20 minutes ago and the agent has since written messages
- **THEN** the thread view shows a recap card above the chat

#### Scenario: Short absence

- **WHEN** the owner opens a thread they last read 2 minutes ago, with new agent messages
- **THEN** no recap card is shown

#### Scenario: Nothing new

- **WHEN** the owner opens a thread whose newest message is older than their last read time
- **THEN** no recap card is shown and no recap is generated

### Requirement: Recaps can be turned off per user

Each user SHALL have a "Show thread recaps" setting, on by default, edited in Settings > Profile next to the utility model and findable through the settings filter. While it is off, no recap card SHALL be shown, no recap request SHALL be made, and no missing-credential hint SHALL be shown. The setting SHALL follow the user across devices. Turning it back on SHALL apply to the next thread opened.

#### Scenario: Default for a new user

- **WHEN** a user who never changed the setting returns to a thread after an absence with new activity
- **THEN** the recap card is shown

#### Scenario: User turns recaps off

- **WHEN** the user turns off "Show thread recaps" and later returns to a thread with new activity
- **THEN** no recap card is shown and no recap generation runs

#### Scenario: Setting applies on another device

- **WHEN** the user turns recaps off on one browser and opens a thread on another
- **THEN** no recap is shown there either

### Requirement: Recap is independent of the agent provider

A recap SHALL be produced from the thread's stored messages and tool calls, the same for every agent provider (Claude, Codex, Gemini, LLM API, …), and SHALL be generated by the user's utility model, never by the thread's own agent or session.

#### Scenario: Codex thread recapped by the utility model

- **WHEN** the owner returns to a thread run by Codex, with the default utility model
- **THEN** the recap is generated by the utility model from the stored transcript, and the Codex session is not resumed

### Requirement: Recap content

A recap SHALL be at most three short sentences in the user's interface language, covering what the agent did, the state the thread is in, and whether the agent is waiting on the user (a pending approval, a question, or an error). It SHALL only summarize activity after the user's last read time, and SHALL be shown as generated text, not as a message of the thread.

#### Scenario: Agent waiting on an approval

- **WHEN** the thread's last activity is a tool call awaiting the owner's approval
- **THEN** the recap says the agent is waiting for an approval

#### Scenario: Recap is not part of the transcript

- **WHEN** a recap is shown
- **THEN** it is not stored as a thread message and is not sent to the agent

### Requirement: Recap visibility is limited to the owner

A recap SHALL be generated only on the thread owner's runner and returned only to the owner. A steer or view sharee SHALL NOT be offered a recap, and a recap request from a non-owner SHALL be refused. Recaps SHALL NOT be offered for sandbox threads.

#### Scenario: Steer sharee opens a shared thread

- **WHEN** a steer sharee opens a thread after an absence with new activity
- **THEN** no recap card is shown and no recap request is made

#### Scenario: Non-owner calls the recap endpoint

- **WHEN** a user who does not own the thread requests its recap
- **THEN** the request is refused with 404 and no runner is asked

### Requirement: Recap input stays within the transcript and limits

The recap input SHALL contain only the thread's stored messages and tool-call names and summaries after the last read time, truncated to a fixed size with the newest activity kept, with project secrets already redacted as stored. Tool outputs beyond a short excerpt SHALL NOT be sent. The generation SHALL have no tools and a single turn, and SHALL time out after 30 seconds.

#### Scenario: Very long absence

- **WHEN** thousands of messages were written since the last read time
- **THEN** the recap is generated from the newest activity within the size limit and still completes

### Requirement: Recap caching and dismissal

A generated recap SHALL be reused for the same thread and the same newest message for the rest of the session, and SHALL be regenerated only when newer activity exists. Dismissing the card, or reading the thread, SHALL hide it until a new recap is offered.

#### Scenario: Reopening the same thread

- **WHEN** the owner leaves and reopens the thread with no new activity in between, during the same session
- **THEN** the same recap is shown, or none if they dismissed it, and no new generation runs

### Requirement: Recap failure is quiet

When the recap cannot be generated (runner offline, no credential for the utility model, timeout, provider error), the thread view SHALL show no recap card and the thread SHALL work normally. A missing credential SHALL be shown once as a hint linking to the utility model setting; other failures SHALL only be logged.

#### Scenario: No Claude credentials with the default utility model

- **WHEN** the owner's runner has no Claude credentials and the utility model is the default
- **THEN** no recap is shown, and a one-time hint points to Settings > Profile > Utility model
